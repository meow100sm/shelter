## 2) Подробное описание диаграмм и как всё работает

### 2.1 ER‑диаграмма (`ер.png`) — данные, сущности и связи

ER‑диаграмма описывает основное содержимое БД. В проекте используется Django ORM, поэтому таблицы отражают модели Django.

#### 2.1.1 `User` (accounts.User)
Задача: хранить учётные записи сотрудников/волонтёров.
- Базируется на `AbstractUser`, поэтому «стандартные» поля (username, password, email и т.д.) присутствуют в БД.
- Доп. поля проекта:
  - `role`: `admin` / `vet` / `volunteer` — роль пользователя, влияет на доступы.
  - `full_name` — ФИО.
  - `totp_secret`, `is_2fa_enabled` — флаги/секрет для 2FA (фактическое устройство хранится в таблицах `django-otp`).

Почему так:
- Использование `AbstractUser` уменьшает объём кода и даёт готовую авторизацию/пароли.
- Роли — простой и прозрачный способ ограничивать доступ (без сложной RBAC‑модели).

#### 2.1.2 `AuditLog` (accounts.AuditLog)
Задача: фиксировать важные действия пользователей (аудит).
- Связь: `AuditLog.user -> User` (FK, `SET_NULL`), чтобы записи аудита сохранялись даже если пользователя удалили.
- Содержит: `action`, `timestamp`, `details`.

Почему так:
- Аудит — требование безопасности/отслеживания действий (логины, изменения сущностей, экспорт и т.д.).

#### 2.1.3 `Animal` (animals.Animal)
Задача: карточка животного в приюте.
Ключевые поля:
- `unique_id` — уникальный номер (UQ), автогенерация `AN-0001`…
- Описание: `name`, `species`, `breed`, `sex`, `birth_date`, `approx_age`, `color`, `features`.
- Приём: `intake_date`, `intake_source`.
- Статус: `status` (intake/quarantine/healthy/treatment/ready/adopted/deceased/transferred).
- Служебные: `created_at`, `updated_at`.

Почему так:
- Статус — главный «агрегированный» признак состояния животного для дашборда/фильтров.
- `unique_id` нужен для бумажных документов и удобного поиска.

#### 2.1.4 `Photo` (animals.Photo)
Задача: хранить фотографии животного.
- Связь: `Photo.animal -> Animal` (FK, CASCADE), у одного животного много фото.
- Поля: `image`, `order`, `uploaded_at`, `uploaded_by -> User (SET_NULL)`.

Как это работает в UI:
- Загрузка фото ограничена до 5 на животное — проверка в представлении перед сохранением.
- Удалять фото можно администратору или тому, кто загрузил.

Почему так:
- CASCADE уместен: фото без животного смысла не имеет.
- `uploaded_by` помогает контролировать права и аудит.

#### 2.1.5 `VetRecord` (animals.VetRecord)
Задача: журнал вет. мероприятий (вакцинации, дегельминтизация, операции…)
- Связь: `VetRecord.animal -> Animal` (FK, CASCADE).
- Поля: `date`, `type`, `description`, `vet_name`, `vet_email`, `next_due_date`, `created_at`.

Как связано с напоминаниями:
- Напоминания завязаны на `next_due_date` и `vet_email`: если через N дней наступает обработка — отправляем письмо.

Почему так:
- `next_due_date` позволяет планировать повторные процедуры и делать автоматические уведомления.

#### 2.1.6 `Movement` (animals.Movement)
Задача: фиксировать перемещения/выбытия (поступление, перемещение, усыновление, смерть, передача другому приюту).
- Связь: `Movement.animal -> Animal` (FK, CASCADE).
- Поля: `date`, `from_location`, `to_location`, `reason`, `notes`, `created_at`.

Бизнес‑логика:
- При некоторых `reason` статус животного автоматически меняется (например, adoption -> adopted).

Почему так:
- История движений важна для отчётности и договоров.

### 2.2 Компонентная диаграмма (`комп.png`) — из чего состоит проект

Диаграмма показывает, что проект — классический Django SSR:

#### 2.2.1 Ядро проекта `shelter/`
- `settings.py` — подключает приложения (`accounts`, `animals`, `reports`) и внешние пакеты (crispy‑forms, django‑otp, django‑filter).
- `urls.py` — маршрутизация:
  - `/accounts/…` → `accounts.urls`
  - `/` (корень) → `animals.urls`
  - `/reports/…` → `reports.urls`

Почему так:
- Простая композиция приложений, каждое отвечает за свой функционал.

#### 2.2.2 Приложение `accounts` (пользователи, роли, 2FA, аудит)
Основные части:
- `accounts.models`: `User`, `AuditLog`.
- `accounts.views`:
  - логин/логаут
  - 2FA verify
  - профиль, смена пароля
  - CRUD пользователей (для admin)
  - просмотр и экспорт аудита
- `accounts.utils.log_action()` пишет в `AuditLog`.
- `accounts.permissions.role_required` ограничивает доступ по ролям.

Как работает 2FA:
- При логине для ролей `admin`/`vet` при наличии подтверждённого `TOTPDevice` делается “pre‑2FA” редирект на ввод кода.
- Настройка 2FA генерирует QR‑код и подтверждает TOTP‑устройство.

Почему так:
- `django-otp` даёт стандартный TOTP без написания криптографии.
- Роли + декоратор — предсказуемая авторизация.

#### 2.2.3 Приложение `animals` (животные, фото, ветеринария, движения)
Основные части:
- `animals.models`: `Animal`, `Photo`, `VetRecord`, `Movement`.
- `animals.views`:
  - дашборд
  - список/карточка/CRUD животных
  - загрузка/удаление фото
  - вет. журнал (таблица + календарь)
  - движения (список/CRUD)
  - генерация договоров (в связке с `reports`)
  - небольшой JSON endpoint `GET /api/animals/`
- `animals.filters.AnimalFilter` — фильтрация списка животных.

Почему так:
- Вся доменная логика “про животных” живёт в одном app.
- Фильтрация через `django-filter` проще и надёжнее ручного парсинга query‑params.

#### 2.2.4 Приложение `reports` (PDF/XLSX и договоры)
- `reports.views.report_form` — форма выбора типа отчёта и формата.
- `reports.generators` — генераторы PDF и Excel:
  - поступления животных
  - ветеринарный журнал
  - движения
  - годовой отчёт
  - договоры (PDF) по шаблону `dogovor.pdf`

Как устроены договоры:
- `dogovor.pdf` — “не форма” (без AcroForm‑полей), поэтому заполнение делается наложением текста (overlay) по координатам.
- Координаты хранятся в `reports/dogovor_placements.json`.
- `reports.dogovor_overlay` строит overlay через ReportLab и мержит с шаблоном через `pypdf`.
- `reports.dogovor_autoplace` (опционально) умеет авто‑детектить координаты по текстовым меткам (PyMuPDF + pdfminer).

Почему так:
- Это самый прямой путь “строго по шаблону PDF”, когда у PDF нет полей.

### 2.3 Диаграмма развёртывания (`разв.jpg`) — как запускается в Docker

В `docker-compose.yml` описаны три контейнера на одном Docker‑хосте:

#### 2.3.1 `db` (PostgreSQL 16)
- Слушает 5432 внутри контейнера.
- Проброс наружу: **host 5433 → container 5432**.
- Данные в volume `postgres_data`.

Почему так:
- Локальный порт 5433 выбран, чтобы не конфликтовать с уже установленным PostgreSQL на хосте.

#### 2.3.2 `web` (Django)
- Запускает приложение и отдаёт HTTP на 8000.
- Бинды:
  - `./media → /app/media` (чтобы загрузки сохранялись на хост)
  - `./staticfiles → /app/staticfiles` (чтобы `collectstatic` сохранял результат)
- Подключение к БД через env `POSTGRES_HOST=db`, `POSTGRES_PORT=5432`.

Почему так:
- Хранение media/staticfiles на хосте удобно для разработки и проверки результатов.

#### 2.3.3 `reminders` (плановые напоминания)
- Контейнер из того же образа, что и `web`.
- Команда: миграции + бесконечный цикл `send_reminders` раз в 86400 секунд.

Почему так:
- Это “лайт” вариант планировщика без Celery/Redis/cron на хосте.
- Изоляция: фоновые задачи не мешают web‑процессу.

Замечание про email:
- `EMAIL_BACKEND` сейчас console‑backend: письма печатаются в лог, а не отправляются наружу.

### 2.4 Структурная/контекстная диаграмма (`струк.jpg`) — как идёт запрос и что с чем связано

Диаграмма описывает поток сверху вниз:

#### 2.4.1 Пользователь → Web UI (SSR)
- Пользователь работает через браузер.
- UI рендерится сервером через Django templates (HTML + CSS + JS).

Почему так:
- Для внутреннего приложения приюта SSR проще: меньше фронтенд‑инфраструктуры и быстрее реализовать.

#### 2.4.2 Web UI → Django Backend (views)
- URL‑маршрутизация ведёт в `accounts.views`, `animals.views`, `reports.views`.
- `role_required` ограничивает доступ по ролям.
- Действия логируются через `log_action` → `AuditLog`.

#### 2.4.3 Django Backend → PostgreSQL (ORM)
- Все сущности (животные, фото, вет. записи, движения, аудит) хранятся в PostgreSQL.
- Доступ — через Django ORM.

#### 2.4.4 Django Backend ↔ Media files
- Фото животных сохраняются на диске в `media/…`.
- В БД хранится ссылка/путь на файл (через `ImageField`).

#### 2.4.5 Django Backend → PDF template `dogovor.pdf`
- Для договоров используется шаблон PDF `dogovor.pdf`.
- Система накладывает текст по координатам (overlay), чтобы получить «заполненный» документ.

#### 2.4.6 Напоминания/отчёты → Email backend
- Напоминания формируются из `VetRecord.next_due_date`.
- Отправка идёт через `send_mail`, но backend сейчас консольный (для dev).

#### 2.4.7 Уточнение по API
- На диаграмме указано «Нет REST API/DRF» — это верно в смысле отсутствия DRF.
- Но в проекте есть **один** небольшой JSON endpoint `GET /api/animals/`.

## 3) Короткая «карта» основных сценариев

1) Логин
- `POST /accounts/login/` → проверка пароля → если для роли `admin/vet` есть TOTPDevice → редирект на `/accounts/2fa/` → ввод кода → `login()`.

2) Работа с животными
- CRUD через формы + шаблоны.
- Список: фильтры `django-filter` + пагинация.
- Карточка: вкладки (база/фото/вет. записи/движения).

3) Вет. журнал
- Таблица с фильтрами и календарный вид.
- Напоминания: раз в сутки выбираются записи с `next_due_date == today + 3 дня` и отправляются на `vet_email`.

4) Договоры
- По движению (усыновление/передача) или по усыновлённому животному.
- Генерация: заполнение шаблона `dogovor.pdf` через overlay.

5) Аудит
- Большинство действий пишет запись в `AuditLog`.
- Есть экспорт в CSV.
