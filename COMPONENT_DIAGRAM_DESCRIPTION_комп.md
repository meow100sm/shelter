**Описание компонентной диаграммы (комп.jpg)**

Данная диаграмма представляет компонентную архитектуру веб‑приложения для управления приютом (PawCare). Её целью является показать логические блоки системы, основные интерфейсы между ними и места интеграции с внешними сервисами и хранилищами данных.

Расположение и элементы диаграммы

- Клиентская часть (слева): блок «Client» содержит «Web client (браузер)». Это пользовательский интерфейс, через который сотрудники приюта и волонтёры взаимодействуют с системой.

- Сервер (центр): большой прямоугольник со стереотипом `<<component>> Server` содержит несколько внутренних компонентов (модулей):
  - `Web UI` — слой представления и маршрутизации HTTP-запросов (Django views/templates или API endpoints);
  - `accounts` — модуль аутентификации и управления пользователями (включая роль‑менеджмент и двухфакторную авторизацию);
  - `animals` — предметный модуль, содержащий модели животных, фотографии, ветеринарные записи и перемещения;
  - `reports` — модуль генерации документов (PDF/XLSX) и экспортов;
  - `reminders job` — фоновой компонент для отправки уведомлений и напоминаний (реализован в проекте как management command / отдельный worker).

- Внешние компоненты (справа и внизу):
  - `Data storage` со значком `PostgreSQL` — реляционная база данных для хранения структурированных данных (модели, связи, индексы);
  - `Media storage` — файл‑хранилище для загруженных фотографий и генерируемых большого бинарного контента (в проекте это `MEDIA_ROOT`, в продакшне рекомендовано объектное хранилище);
  - `External services: SMTP` — внешний почтовый сервер, используемый для отправки уведомлений.

Интерфейсы и потоки данных

- Между компонентами сервера показаны интерфейсы вида `IAuth`, `IAnimals`, `IAudit`, `IMovement`, `IVetJournal`, `IReports`. Они означают логические API/контракты, через которые модули взаимодействуют друг с другом:
  - `Web UI` использует `IAuth` для операций входа/выхода и управления сессиями;
  - `animals` предоставляет интерфейс `IAnimals` для операций CRUD по карточкам животных, фотоматериалам и истории;
  - `reports` подписан на данные `animals` и `accounts` через `IReports` для формирования выгрузок и договоров;
  - `reminders job` читает данные ветжурнала (`IVetJournal`) и вызывает `IEmail` для отправки уведомлений через SMTP.

- База данных (`IDatabase`) и файловое хранилище (`IFileStorage`) доступны нескольким компонентам: `accounts`, `animals`, `reports` и `reminders job` читают/записывают данные и файлы, причём большие бинарные данные (фото, итоговые PDF) направляются в `Media storage`.

Дизайнерские и архитектурные решения, отражённые на диаграмме

1. Монолит с модульной организацией
   - Диаграмма отражает монолитный подход (всё внутри одного «Server»), но с чётким разделением на модули. Это согласуется с подходом Django: один проект, несколько приложений (`accounts`, `animals`, `reports`). Такой дизайн упрощает развертывание и обмен данными (нет необходимости обеспечивать сетевой доступ между микросервисами), при этом логическая модульность повышает читабельность кода и облегчает тестирование.

2. Явное разделение структурированных данных и файлов
   - PostgreSQL используется для структурированных сущностей (животные, записи, пользователи). Медиа хранится отдельно — это полезно по двум причинам: базы данных не оптимальны для хранения больших бинарных данных, и файловое хранилище легко масштабировать независимо (например, S3). Диаграмма подчёркивает это разделение через отдельные компоненты `Data storage` и `Media storage`.

3. Внешние интеграции минимизированы
   - SMTP вынесен как внешний сервис: приложение не включает встроенный почтовый сервер, оно использует стандартный протокол для отправки писем. Это делает систему более гибкой и безопасной (smtp-сервис можно заменить без изменения бизнес‑логики).

4. Отдельный фоновый компонент для напоминаний
   - `reminders job` на диаграмме показан отдельно от `Web UI`, что отражает архитектурную рекомендацию: фоновые задачи должны выполняться вне жизненного цикла HTTP‑запроса. В текущей реализации это management command, запускаемая как отдельный процесс (или в контейнере) по расписанию. При увеличении нагрузки такой компонент можно заменить на очередь задач (Celery, RabbitMQ) без изменения модели данных.

5. Интерфейсы как контракт между модулями
   - Стереотипы интерфейсов (`IAnimals`, `IReports` и т.д.) символизируют контракты, которые делают взаимодействие модулей предсказуемым. В коде это соответствует явным функциям/сервисам (например, набор публичных методов в `reports/generators.py`, функции из `animals/services.py` или well‑defined Django view endpoints), что облегчает модульное тестирование.

Практическое значение диаграммы для дипломной работы

- Диаграмма даёт читателю ясное представление о границах ответственности: какие сущности хранятся в БД, какие — в файловом хранилище, какие операции выполняются синхронно из Web UI, а какие — асинхронно фоновыми задачами.
- В тексте диплома можно ссылаться на диаграмму при объяснении архитектурных решений: выбор монолита ради простоты развёртывания, выделение фоновых задач ради устойчивости, и разделение медиа/метаданных ради масштабируемости.
- Диаграмма также служит основой для раздела «Пути улучшений»: миграция фоновых задач на Celery, перенос медиа в S3, вынесение heavy‑work в отдельные сервисы и введение кэширования (Redis) между `Web UI` и `Data storage`.
