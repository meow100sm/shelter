# Пояснение к диаграмме компонентов (PlantUML) — 2026-05-27

Файл диаграммы: component_diagram.puml

## 1) Что в диаграмме является «компонентами»

В UML-диаграмме компонентов **компонент** — это отдельный заменяемый модуль системы с чёткой ответственностью и точками взаимодействия (интерфейсами). На PlantUML это элементы, объявленные ключевым словом `component` (и также `database` как специализированный элемент).

В текущем варианте диаграммы:

- **Компоненты (component/database):**
  - Web client (браузер) — внешний программный модуль, который инициирует HTTP-запросы.
  - Web UI (templates/static) — часть серверного приложения, отвечающая за отображение страниц (HTML/CSS/JS) и формы.
  - accounts / animals / reports — серверные компоненты, соответствующие Django-приложениям (apps).
  - reminders job (send_reminders) — отдельный исполняемый модуль (management-команда/процесс), запускаемый по расписанию.
  - PostgreSQL — компонент хранения данных (СУБД).
  - Media storage (MEDIA_ROOT) — компонент файлового хранения пользовательских файлов (фото).
  - SMTP — внешний сервис отправки писем.

- **Пакеты (package) НЕ являются компонентами.**
  - «Клиент», «Сервер (Django)», «Инфраструктура» — это **группировка** для читаемости: они показывают границы развертывания/ответственности, но сами по себе не являются компонентами.

Итого: «клиент», «Django сервер» и «инфраструктура» как подписи пакетов — **не компоненты**, а контейнеры (группы). Компоненты — то, что внутри них.

## 2) Как читать «леденец на палочке» в этой диаграмме

- Связь вида `COMP -down- IInterface` (где `IInterface` объявлен через `interface`) означает:
  - компонент **предоставляет** (реализует, экспонирует) этот интерфейс наружу.
  - на рисунке это выглядит как «леденец» (лепесток/кружок у компонента).

- Связь вида `A ..> IInterface : <<requires>>` означает:
  - компонент **требует** (использует) этот интерфейс, то есть зависит от функциональности, предоставляемой другим компонентом.

Важно: в UML “provided/required” обычно отображаются “ball-and-socket”. В PlantUML проще и читабельнее показать: **provided** как lollipop, а **required** как dependency-стрелку со стереотипом `<<requires>>`.

## 3) Интерфейсы бизнес-уровня (приложение)

Ниже — все интерфейсы приложения, кто их предоставляет и кто использует.

### IAuth
- **Предоставляет:** accounts (ACC)
- **Требует:** Web UI (UI)
- **Почему так:** логика входа/выхода и 2FA (TOTP) сосредоточена в приложении accounts; UI вызывает этот функционал при аутентификации пользователя.

### IAudit
- **Предоставляет:** accounts (ACC)
- **Требует:** animals (ANM), reports (RPT)
- **Почему так:** в проекте аудит реализован через модель AuditLog и вспомогательную функцию логирования (log_action), которая относится к домену accounts. Другие подсистемы фиксируют события через аудит.

### IAnimals
- **Предоставляет:** animals (ANM)
- **Требует:** Web UI (UI), reports (RPT), reminders job (REM)
- **Почему так:** CRUD животных, список/карточка/поиск — ответственность animals; UI обращается к этому функционалу напрямую, отчёты берут данные по животным, reminders использует данные животных как часть выборок/напоминаний.

### IVetJournal
- **Предоставляет:** animals (ANM)
- **Требует:** reports (RPT), reminders job (REM)
- **Почему так:** ветеринарные записи и логика «следующих дат» находятся в animals (VetRecord и обработка выборок). Отчётам нужны статистики/выборки, а reminders использует next_due_date.

### IMovement
- **Предоставляет:** animals (ANM)
- **Требует:** reports (RPT)
- **Почему так:** движения животного (Movement) принадлежат домену animals. Отчёты используют агрегирование по перемещениям.

### IReports
- **Предоставляет:** reports (RPT)
- **Требует:** Web UI (UI)
- **Почему так:** генерация PDF/Excel и договоров — ответственность reports; UI запускает генерацию и отдаёт пользователю файл.

Примечание: в упрощённой диаграмме не выделялись интерфейсы уровня `IPhotos`, `IUsers` и т.п., чтобы не перегружать рисунок. При желании их можно добавить отдельной «детализированной» диаграммой.

## 4) Инфраструктурные интерфейсы

### IDatabase
- **Предоставляет:** PostgreSQL (DB)
- **Требует:** accounts (ACC), animals (ANM), reports (RPT), reminders job (REM)
- **Почему так:** все серверные компоненты читают/пишут данные через ORM Django, что физически означает зависимость от СУБД.

### IFileStorage
- **Предоставляет:** Media storage (FS)
- **Требует:** animals (ANM), reports (RPT)
- **Почему так:** animals сохраняет и выдаёт фото животных (ImageField, MEDIA_ROOT), reports может формировать файлы (PDF/Excel) и выдавать их как результат (в демонстрации — как файловый ответ/временный файл).

### IEmail
- **Предоставляет:** SMTP
- **Требует:** animals (ANM), reminders job (REM)
- **Почему так:** отправка email для напоминаний — внешняя инфраструктурная функция; сама логика выбора адресата/события внутри приложения, но доставка — через SMTP.

## 5) Почему интерфейсы расставлены именно так (коротко)

- Интерфейсы выделены по **границам ответственности** Django apps:
  - accounts: аутентификация/2FA + аудит;
  - animals: домен животных, ветеринария, движения, фото;
  - reports: генерация отчётов.
- «Требуемые» связи показаны у тех компонентов, которые **используют** функциональность других:
  - UI требует IAuth/IAnimals/IReports,
  - reports требует данные животных/ветжурнала/движений,
  - animals/reports требуют аудит,
  - почти все требуют базу данных.
- Инфраструктура вынесена отдельно, потому что это **внешние сервисы**, без которых приложение не работает, но которые не являются частью бизнес-кода.
